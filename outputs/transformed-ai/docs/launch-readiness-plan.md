# TransformED AI — Launch Readiness Plan

Companion to `product-audit.md` and `user-personas.md`. Findings are prioritized P0 (must fix before any real student, minor or adult, touches the product) / P1 (must fix before scaling past a small closed pilot) / P2 (roadmap — sequence after launch).

---

## P0 — Launch blockers

These are not "more features needed" — they are places where the product's current behavior contradicts its own stated promises, its legal obligations, or basic trust with a paying customer.

| # | Finding | Why it's P0 | Suggested owner/fix |
|---|---|---|---|
| P0-1 | **No age-gating or parental-consent mechanism anywhere in the product**, despite webcam-based attention monitoring of a likely-minor user base (see Persona: Ananya). Not tracked in the defect register or deferred-work log — the team does not currently treat this as a known gap. | Direct legal/ethical exposure under India's DPDP Act (which has specific verifiable-parental-consent provisions for children's data) and basic child-safety practice for an education product. This is the single highest-risk finding in the audit. | Add a date-of-birth field to sign-up; route consent for the attention-monitoring feature through a parent/guardian account for under-18 users; block camera-based monitoring entirely for unverified-minor accounts until a guardian consent flow exists. |
| P0-2 | **Account-deletion button has no click handler.** The database schema and cascade logic support right-to-erasure, but a user literally cannot trigger it from the UI. | DPDP right-to-erasure must be actually exercisable, not merely schema-supported. A support ticket or regulator request would currently have no self-serve path. | Wire the existing "Delete Account" button (`apps/web/src/components/settings/tabs/AccountTab.tsx`) to the deletion flow; also close the known gap where PostHog analytics profiles are never erased on deletion. |
| P0-3 | **Brand-name inconsistency in the live product** — onboarding renders "HIEIQ.AI" and sign-up copy says "Join HIE" instead of TransformED AI. | This is visible on the very first screen a new customer sees. A go-to-market audit exists specifically to catch this kind of thing before a paid ad or demo sends someone there. | Grep/replace remaining "HIE"/"HIEIQ" strings in the frontend; add a copy-review pass to the pre-launch checklist. |
| P0-4 | **Whole-book lesson generation is unverified.** The acceptance run proving the flagship fix for the original "silently generated a lesson from 4% of a 1,151-page book" defect has been blocked since 2026-08-05 on a zero API balance; the underlying ~90,000-character context-window cap that caused it is still architecturally unfixed, only now surfaced instead of silent. | This is the core product promise — "give me a lesson from my textbook chapter." Launching without this verified risks repeating the exact defect that prompted the team to write an entire "Scale Contract" document about it. | Fund and run the blocked Phase 7 acceptance test; treat the 90k-char cap as an open architecture item, not a closed one, until chapter-length coverage is actually re-derived per the Scale Contract. |
| P0-5 | **Self-declared "first paying student by Week 10" milestone is unmet as of today**, and Sprint 4 (load testing, Stripe payment integration, hardening) is largely untouched — payments are not wired up at all. | You cannot launch to paying customers without a way to take payment, and the team's own tracking shows this work hasn't started. | Sequence Stripe integration and a real load test as the literal next sprint before any external launch date is set. |
| P0-6 | **India data residency is not yet real.** Supabase (the database) is already in Mumbai, but compute (FastAPI/ARQ) and Redis are still on infrastructure outside India, despite this being a stated DPDP prerequisite the team itself wrote down as required "before real students join." | Matches a legal/compliance commitment the team has already made to itself; shipping without it undermines the DPDP compliance story entirely. | Execute the already-designed ADR-001 migration (provider choice — Fly.io Mumbai / Render Singapore / AWS ap-south-1 — is the only open decision) before onboarding real students. |
| P0-7 | **Prior full-stack integration audit found most routes broken despite passing backend tests** (11 of 12 backend↔frontend integration points were mocked, dead, or broken in a "360-audit," including quiz answers rendering as incorrect due to a field-name mismatch). No evidence a fresh equivalent audit has been run since major recent changes. | Green tests are not proof this product works end-to-end for a real user — the team's own audit history says so directly. Launching without re-verifying this risks a demo-breaking or trust-breaking bug on day one. | Re-run a full-stack "does this actually work with a real account, real upload, real payment, real session" pass immediately before any launch date, not just before a sprint close. |

## P1 — Fix before scaling past a small closed pilot

| # | Finding | Why it matters | Suggested fix |
|---|---|---|---|
| P1-1 | CES intervention thresholds, cooldown timing, and message copy are launch-day defaults, never tuned against real session data (the tuning docs are explicitly empty templates awaiting ≥20 real sessions). | Untuned interventions risk feeling patronizing or annoying — the opposite of the intended "attentive tutor" effect. | Run the closed pilot below specifically to gather ≥20 sessions, then execute the already-written tuning process. |
| P1-2 | "Learner DNA" does not currently feed back into lesson planning/pacing/difficulty anywhere in the pipeline — it's a report feature, not an adaptive engine. | Marketing this as adaptive personalization would misrepresent the current build to a discerning user (see Persona: Rohan). | Either scope a fast-follow to make DNA actually influence generation, or adjust launch messaging to "engagement insights + personal learning report" until it does. |
| P1-3 | Accessibility is thin — only a fraction of frontend components use ARIA attributes, and no keyboard-navigation handling was found anywhere in the codebase. | Real risk for an education product, and an increasingly explicit legal expectation in several markets. | Add a keyboard-nav and screen-reader pass to the pre-scale checklist, prioritizing the quiz, teach-back, and consent-modal flows first. |
| P1-4 | No real unit economics exist — the $3/lesson ceiling is enforced in code, but only ~23 lessons have ever been generated and no cost-per-lesson benchmark has been run at volume; the built eval harnesses (5-PDF, 20-PDF) have never actually been executed. | Pricing tiers (₹799/₹999/₹1,499) were presumably set against an assumed cost structure — that assumption is currently unvalidated. | Run the existing eval harnesses for real before finalizing pricing commitments to paying customers. |
| P1-5 | Vendor fragility: the image-generation fallback provider (Imagen 4 Fast) is already dead with no replacement decided; the LLM "provider abstraction" only has one vendor actually wired despite documentation implying easy swapping; frontend has zero error/analytics observability (no Sentry/PostHog client-side) despite it being configured. | Reduces resilience and blinds the team to real user-facing errors post-launch. | Decide and implement the image-fallback replacement; wire frontend observability before opening to real traffic. |
| P1-6 | Assessment retake gaming: teach-back can be retried an uncapped number of times with no per-session cost ceiling, and DNA accuracy is computed over full retake history rather than the latest attempt (a student who fails 9 times then passes scores ~10%, not 100%). | Both a cost-control gap and a fairness/product-correctness issue. | Cap retakes or their cost exposure; fix DNA scoring to weight recent attempts appropriately. |
| P1-7 | Real production-scale load testing (the WebSocket load-test harness) has only been run against an in-process stub, never against live infrastructure. | The tutor's real-time interventions are a core differentiator — if they break under real concurrent load, that's the worst possible first impression. | Execute the already-built load test against the real (post India-migration) infrastructure before opening beyond the closed pilot. |

## P2 — Roadmap, sequence after launch

- Admin panel (found unimplemented as of late July) — needed for ops visibility as volume grows, not for the first cohort.
- Revision/re-watch video mode (Bunny Stream compiled video) — explicitly decided but not designed or implemented; fine to hold for a v1.1.
- Adaptive onboarding placement — today's onboarding is a fixed 20-question style survey, not a leveling test; a genuinely adaptive placement flow is a strong v2 differentiator.
- Multilingual support — despite the product's clear India focus and Indian-language TTS, chunking/embedding math for non-English text (Hindi/Tamil) is currently broken and explicitly deferred as English-only. Given the target market, this is a real market-fit gap worth an early roadmap slot, not a distant one.

## Recommended sequencing

1. **Now → 2–3 weeks:** Close all P0 items. Most are narrow, well-understood fixes (a button handler, a string replace, a migration execution, a blocked test run) rather than new engineering — the child-safety gap (P0-1) is the one that needs real design thought, not just a code fix, and should start immediately given its severity.
2. **In parallel:** Run a small closed pilot with already-consenting adults only (no minors, sidesteps P0-1 risk while it's being designed) to generate the real session data P1-1 and P1-4 depend on, and to re-run the full-stack integration check from P0-7 under real usage.
3. **Before public launch:** Clear P1 items surfaced by the pilot, finalize pricing against real cost data, and complete the India data-residency migration.
4. **Launch messaging:** Scope claims to what's true today — "engagement-aware tutoring, teach-back verification, and a personal learning report" — and hold "adaptive personalization that changes your lessons for you" for when Learner DNA actually closes that loop (P1-2).
5. **Post-launch roadmap:** P2 items, sequenced by the multilingual gap first given how central the Indian-language positioning is to the product's identity.
