# Deferred Work

## Deferred from: code review of 3-22-posthog-assessment-events (2026-07-03)

- **DEFER-001** — UUID `distinct_id` sent to PostHog with no erasure pathway for DPDP right-to-erasure. PostHog builds a persistent person profile keyed on the user's internal UUID; no code path calls PostHog's person-delete API when an account is deleted. Addressable in a dedicated DPDP compliance story before real-student launch.
- **DEFER-002** — Synchronous `posthog.capture()` called from async route handlers and service functions (no `asyncio.to_thread` guard). Current PostHog Python SDK v3 queues internally and returns in microseconds — no measurable event-loop impact today. Add `asyncio.to_thread` wrapper if SDK v4 changes flush semantics.

## Deferred from: code review of 2-43-notifications-ui (2026-08-06)

- **DEFER-003** — `useNotificationPreferences`'s PATCH failure handling collapses 503 (retryable)/500/401/403 (session-expired) into identical treatment (log + conditional rollback), with no retry-on-503 and no re-auth prompt on 401 (`apps/web/src/hooks/useNotificationPreferences.ts`). Matches how every other non-critical settings toggle in this codebase already behaves — a session-expiry UX improvement is cross-cutting, not specific to notifications.
- **DEFER-004** — `useNotificationPreferences` (like `useAttentionConsent` on the sibling `sprint3-master` branch) checks only `!userId`, never `useAuth()`'s own `isLoading`, so it can't distinguish "auth still resolving" from "genuinely logged out" — causing a brief flash of default values on a fresh page load before the real row loads. Confirmed identical pattern in `apps/web/src/hooks/useAttentionConsent.ts` (Story 2-42) — a shared gap across both hooks needing a single fix (e.g. exposing and checking `AuthContext`'s `isLoading`) once the branches converge, not a per-hook patch.
- **DEFER-005** — The AC-5 request-generation race guard in `useNotificationPreferences.ts` is scoped to one hook instance (one browser tab/mount), not one user/account. Two tabs open on the same settings page can each report a successful toggle while persisting two different final values server-side, with no cross-tab reconciliation — no realtime subscription or `BroadcastChannel` exists anywhere in `apps/web/src` today. Closing this needs a realtime-sync mechanism this codebase doesn't have yet.
- **DEFER-006** — `settingsService.updateNotifications`'s entire caller contract (rollback, logging, race guard) depends on `api.patch` throwing on a non-2xx response, which is assumed, not verified anywhere. Shared assumption across every other real service in this codebase (`books.service.ts`, `onboarding.service.ts`, `lib/assessment.ts` all rely on the same axios instance) — not new to this diff, but never premise-tested anywhere either.
- **DEFER-007** — `useNotificationPreferences.ts`'s `.maybeSingle<NotificationPreferences>()` generic is a compile-time assertion only, not runtime-validated — a partially-null row or a renamed column would still type-check as four non-null booleans. Same unaudited shape as `useAttentionConsent.ts`'s own Supabase read on the sibling branch — fixing only one would be inconsistent; needs a project-wide premise test once merged together.
- **DEFER-008** — Brittle DOM-structure-coupled test selectors (`closest('div.flex.items-center.justify-between')`) and log-message string-matching assertions (`stringContaining('failed to read')`) in `useNotificationPreferences.test.ts`/`NotificationsTab.test.tsx`. Matches this codebase's own pre-existing, widely-used testing convention (including the `NotificationsTab.test.tsx` this replaced) — not a regression introduced here, but a systemic testing-convention gap.
