# Story BR-5 — Deploy-time required-secrets verification (closes D146's residual gap)

Status: done — 8-layer `/bmad-code-review` complete 2026-09-04, 11 patches applied, 1 finding deferred (D151), 3 findings independently re-verified and refuted

## Story

As Dev 4 (picking this up opportunistically — it is not squarely WS/JWT/tutor-FSM domain, but
surfaced directly out of BR-2's review chain and D146's investigation),
I want the deploy pipeline to verify, before `flyctl deploy` runs, that every secret the app's own
startup guards require is actually present on the target Fly app,
so that a correctly-implemented fail-loud guard (like D49's) never again produces a silent,
multi-hour production crash-loop (D146) that nobody notices until Fly's retry budget is already
exhausted.

## Background

- **D49** (closed, PR #159/Story 5-4): added `assert_rate_limit_storage_configured()` —
  correctly raises `RuntimeError` at boot outside debug mode if `RATE_LIMIT_STORAGE_URL` resolves
  to in-process `memory://` storage.
- **D146** (open, logged 2026-09-03): the guard fired exactly as designed on every boot attempt
  after PR #159 deployed, because `RATE_LIMIT_STORAGE_URL` was never set as a live Fly secret.
  Both `hie-api` machines (`api` and `worker`) crash-looped for ~3 hours (02:51–05:58 UTC) before
  anyone noticed — Fly's `on-failure` policy exhausted `max_retries: 10` and gave up silently (no
  alert exists; W10-2 monitoring is not built). D146's own disposition names the gap this story
  closes verbatim: *"nothing currently diffs 'secrets a story's code depends on' against 'secrets
  actually deployed.'"*
- **D145** (open, separate but same class): `hie-api`'s live Fly region list silently drifted from
  `fly.toml`'s committed `primary_region = "bom"` — a different instance of the same root problem
  (live Fly configuration state diverging from what the repo assumes, with nothing to catch it).
  This story does not fix D145 (region drift isn't a "secret," `flyctl secrets list` doesn't see
  it) but is worth naming as the sibling gap in the same family.

The guard itself is not the defect. Fail-loud-at-boot is the correct pattern (CLAUDE.md's own
"silent truncation/degradation is never acceptable" rule) and this story does not touch it. The
defect is that **nothing verifies, before a deploy is attempted, that the environment a guard
depends on is actually configured** — so "the code is correct" and "the deploy will succeed" are
two different, unverified claims currently conflated.

## Acceptance Criteria

1. A single, anti-drift source of truth for "secrets required for a non-debug `hie-api` boot"
   exists in `scripts/check_fly_secrets_configured.py`, built from two sources:
   - Every `pydantic.Field` in `app.config.Settings` with no default, introspected live via
     `Settings.model_fields` — never hand-copied, so a future story adding a new required
     `Settings` field is automatically covered with no separate list to remember to update.
   - Every env var gated by a custom fail-loud startup assertion whose value has a *non-raising*
     pydantic default (so pydantic alone would never catch it) — currently exactly one:
     `RATE_LIMIT_STORAGE_URL` (`assert_rate_limit_storage_configured`, D49). Hand-listed, backed
     by a source-scan test (AC5) proving the name still appears in that guard's own module, so
     the two can't silently drift apart the way the underlying app code already did once.
2. `scripts/check_fly_secrets_configured.py --app <name>` calls `flyctl secrets list --app <name>
   --json` (names only — `flyctl` never exposes secret values, and this check only ever needs
   presence, so no secret material touches CI logs), diffs required vs. present, and:
   - exits `0` with a clear confirmation line if every required secret's name is present;
   - exits `1` and prints every missing secret's name plus which guard/field requires it if
     anything is absent;
   - exits `1` with a distinguishable error message (never a silent pass) if `flyctl` itself
     fails, times out, or returns unparseable output — "couldn't verify" must never be reported
     as "verified OK."
3. `.github/workflows/deploy.yml` runs this check as its own step, using the already-configured
   `FLY_API_TOKEN` secret, **before** the `flyctl deploy --remote-only` step — so a deploy with a
   missing required secret fails the GitHub Actions job loudly, before Fly ever attempts to boot
   the app and burns its retry budget the way it did for D146.
4. The pure diff logic (`list_missing_secrets`) is unit-tested directly (empty / partial / full
   coverage) without shelling out to a real `flyctl` process.
5. A guard test proves the two anti-drift claims in AC1 actually hold:
   - the pydantic-derived portion of the manifest is generated by calling
     `Settings.model_fields` at test time and comparing to what the script reports (not a
     hand-copied list that could go stale the next time a required field is added or removed);
   - `RATE_LIMIT_STORAGE_URL` is confirmed present, by source scan, in
     `app.core.rate_limit`'s guard — so if a future refactor renames that env var in one place
     and not the other, this test reddens instead of the drift going unnoticed a second time.
6. `docs/DEFECT-REGISTER.md` gets a new entry — **D150** — documenting this fix, explicitly citing
   D146 (the incident that surfaced the gap) and D145 (the sibling live-config-drift class), per
   binding rule 5 (a documented limitation needs its own register ID, not just prose inside
   another entry's disposition). Per binding rule 7, the CI step (AC3) is what makes this
   `FIXED`, not `FIXED-UNGUARDED` — the register entry must cite it, not just the script's
   existence.

## Scale & Load

1. **What is ONE unit of work, and what is its range?**
   One unit is one CI-triggered deploy attempt against one Fly app (`hie-api`, `fly.toml`'s only
   declared app — ADR-001 §3 explicitly rejects splitting into multiple Fly apps). Range: exactly
   one app, one secrets list, one check, once per deploy — not a per-user or per-request
   operation. `flyctl secrets list` for this app currently returns a small, bounded set (the 8
   pydantic-required fields + 1 guard-enforced var = 9 names today, matching the References
   section below; realistically low tens even after several more stories add required config).
   This is not a scale-sensitive path. **[Review Finding — corrected 2026-09-04]** An earlier
   draft miscounted this as "6 + 1 = 7," disagreeing with this story's own References section,
   which correctly listed all 8 fields — corrected to match the real count in
   `apps/api/app/config.py`, verified directly by three independent review layers.

2. **Which budgets are FIXED while the input VARIES — and what happens past them?**
   N/A — no fixed-size budget applies here. The required-secrets manifest grows exactly as fast
   as `Settings.model_fields` and the hand-listed guard set grow; nothing is truncated or capped.
   The one thing that must never silently degrade is the *check itself* failing open: if `flyctl`
   errors, times out, or returns something unparseable, AC2 requires an explicit `exit 1`, never a
   quiet pass — this is the one place this story's own logic could reproduce D146's shape
   (a check that looks like it ran but didn't actually verify anything), so it's covered directly
   by AC2/AC4, not left as an assumption.

3. **What is the SCOPE of every limit — per user, per instance, or per deployment?**
   Per deployment. One Fly app, one secrets namespace (`fly secrets` are app-scoped, not
   per-machine/per-process — `api` and `worker` share the same secret set per `fly.toml`'s single
   `[build]`/two-`[processes]` layout), one CI check per deploy attempt. No per-user or
   per-instance dimension exists in this problem.

4. **Which reads and writes are UNBOUNDED?**
   None. `flyctl secrets list --app hie-api --json` returns one bounded JSON array (secret names
   only, no values, no pagination — Fly's own secrets API has no documented case of an
   unbounded/paginated response for a single app). No Supabase read or write is introduced;
   `tests/unit/test_unbounded_queries.py`'s source scan is unaffected by this story.

5. **Which caps were INHERITED from an earlier design, and have they been re-derived?**
   N/A — this is a new mechanism with no prior cap to inherit or re-derive.

6. **Is every check-then-act sequence safe under CONCURRENT requests?**
   Partially — narrower than an earlier draft of this answer claimed. `deploy.yml`'s
   `concurrency: { group: deploy-hie-api, cancel-in-progress: false }` genuinely serializes
   overlapping *workflow runs* of this file, so two concurrent deploy attempts can't race each
   other's verify/deploy steps. **[Review Finding — corrected 2026-09-04]** That guarantee does
   **not** cover a real, if narrow, race: an external actor (a human operator, a secret-rotation
   script) unsetting or changing a required secret in the multi-second window between the "Verify
   required Fly secrets are configured" step finishing and "Deploy to Fly.io" starting, within
   the *same* already-running job. If that happens, the verify step has already printed `OK` and
   exited 0 before the mutation, `flyctl deploy` proceeds anyway, D49's own boot guard fires on
   the freshly-deployed machines, and the app crash-loops — reproducing D146 despite the job
   having reported the secrets check as passed. **Not fixed here**: Fly's secrets API has no lock
   primitive to close this with code (registered as part of **D151**, alongside the
   values-not-checked gap below — same root cause, "the verify step's OK is a point-in-time
   snapshot, not a guarantee that holds until deploy actually runs").

## Dev Notes

- **Why this isn't scoped to "add monitoring/alerting."** D146's own disposition separately names
  "no alert exists (W10-2 monitoring isn't built yet)" as a distinct, larger, already-tracked gap
  (CLAUDE.md's Build Roadmap, Week 10). This story is deliberately the narrower, immediately
  actionable piece: catch the missing secret in CI, before Fly ever boots, rather than requiring a
  monitoring stack that doesn't exist yet to catch it after boot.
- **Why the manifest is introspected, not hand-maintained.** The exact failure class this story
  guards against — "the code's real requirement and someone's separately-maintained understanding
  of it silently diverge" — is what happened once already (D49's fix existed in code; the
  deployed environment's secret set was a human's separate, unverified assumption). A hand-typed
  Python list of required env var names would reproduce the identical risk one layer up. Deriving
  the pydantic-required portion directly from `Settings.model_fields` removes that whole class for
  every future required `Settings` field, at zero ongoing maintenance cost.
- **Why `RATE_LIMIT_STORAGE_URL` still needs a hand-listed entry.** It is not (and should not
  become) a required `Settings` field — `memory://` is a legitimate default for local
  single-process development (`assert_rate_limit_storage_configured`'s own `debug=True` exemption
  depends on this). The guard's requirement is conditional ("required outside debug"), which
  pydantic's plain required/optional model can't express — hence the second, explicitly
  anti-drift-tested source.
- **`flyctl` availability in CI.** `deploy.yml` already installs a pinned `flyctl` version
  (`0.4.77`, pinned 2026-08-17 per that file's own comment — "latest" broke auth from this
  runner) before its deploy step; Task 2's new step reuses that same installed binary, added
  nothing new to install.
- **Testing standard**: per CLAUDE.md's Defect Register binding rule 2, `_fetch_configured_secret_names`'s
  failure-path tests must assert the real raised exception / real exit code — not merely that
  `subprocess.run` was called with certain arguments.
