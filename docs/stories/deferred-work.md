- **No `idempotency_key` on `stripe.checkout.Session.create`** — a client-side or infra-level network retry of `POST /create-checkout-session` creates a second, independent Checkout Session rather than returning the original. ## Deferred from: code review of story 3-54 (2026-08-13, onboarding lock + HIE rebrand)

- **D73 — No TTL on Redis `onboarding_key`** — `router.py:250`: `redis.set(onboarding_key, "1", nx=True)` has no `ex=` or `px=` TTL. A process crash (SIGKILL, `CancelledError`, `MemoryError`) between line 250 and the router's `except HTTPException` cleanup at line 265 leaves the key set forever, permanently locking the user out with no self-healing path. Not introduced by Story 3-54 (pre-existing); only the normal HTTPException path was fixed. **Fix:** add `ex=86400` as a safety-net TTL, or a health-check job to detect orphaned keys. Registered as D73. Owner: Dev 4. [apps/api/app/modules/assessment/router.py:250]
- **Broad `except Exception` in Step 4 launders non-retryable OpenAI errors as HTTP 503** — `service.py:1017`: the `except Exception` block catches `openai.AuthenticationError` (key revoked), `openai.PermissionDeniedError`, and coding bugs (`AttributeError`, `TypeError`) alongside genuine transient failures, converting all of them to "please retry." A client with a permanently revoked key gets the same 503 as one that hit a rate limit, and will retry indefinitely with wasted quota and no useful signal. The provider's `@with_retry` already skips retrying on 400/401, so the escaping exception represents a permanent failure — but the service layer doesn't propagate that distinction. Fix: check `isinstance(exc, openai.AuthenticationError | openai.PermissionDeniedError)` and raise HTTPException(500) instead of 503 for those. Requires importing openai in service.py. [apps/api/app/modules/assessment/service.py:1017]
