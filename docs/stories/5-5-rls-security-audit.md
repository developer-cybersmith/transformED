# Story 5-5 — RLS security audit on all Supabase tables

Status: ready-for-dev

## Story

As a platform operator preparing TransformED for its first paying student,
I want every Supabase table's Row Level Security enabled and its policies verified — with real minted JWTs against the live project, not just the Postgres test shim — and the `attention_events` DPDP consent gate confirmed end-to-end,
so that no student can ever read, write, or infer another student's rows, no table is reachable without an authenticated JWT, and the Epic-5 "platform operator is confident every table has correct RLS" goal is evidence-backed rather than assumed.

## Acceptance Criteria

1. **Full table inventory matches reality.** The audit report enumerates every table that actually exists today (15 live tables: `users`, `lessons`, `lesson_jobs`, `chapters`, `chunks`, `sessions`, `quiz_attempts`, `teachback_attempts`, `learner_dna`, `onboarding_responses`, `session_events`, `attention_events`, `books`, `user_consents`, `user_notification_preferences`), and explicitly reconciles this against Epic-5's aspirational list — noting that `embeddings` was created and later **dropped** (`20260625000000_chunks_inline_embedding.sql` step 6), that `lesson_packages` is **not a table** (it is the `lessons.content` JSONB column, written by `package_builder_node`, already covered by the `lessons` RLS policy), and that `lesson_access`, `stripe_events`, and `profiles.is_admin` **do not exist yet** (depend on Story 5-3 / S4-3 and the not-yet-scheduled admin-panel work).
2. **Every live table has `ENABLE ROW LEVEL SECURITY` and a full CRUD policy set**, verified by reading the actual migration SQL (not inferring from the tracker's "✅ Enabled in both migrations" claim) — cross-checked against the live Supabase project's `pg_tables.rowsecurity` / `pg_policies`, since migration intent can drift from a project's actual state (dashboard-applied changes, partial applies).
3. **Ownership predicates are correct for every table**, including the multi-hop join chains: `lesson_jobs`/`sessions`-descendants join to `lessons`/`sessions`; `chapters`/`chunks` join to `books` (re-rooted from `lessons` in `20260803000000_chapters_book_scoped.sql` when the ingestion unit changed from lesson to book — confirm no stale lesson-rooted policy survives anywhere). Verified with three minted-JWT principals per table: the row's real owner, a "stranger" authenticated user, and no JWT at all (anon key) — owner sees only their own rows and can write only their own rows; stranger and anon see zero rows and every write attempt is rejected.
4. **`attention_events`'s consent gate is verified per-command, not assumed uniform.** Confirm SELECT/INSERT/UPDATE all require `users.attention_consent = true` (`20260611000000_initial_schema.sql:795-832`); confirm INSERT additionally requires a live `user_consents` row with `consent_type = 'attention_tracking'` (dual DPDP check added in `20260702000000_dpdp_user_consents.sql:99-121`); and **explicitly document, as an audit finding, that DELETE (`:834-844`) and UPDATE were never upgraded to the dual-check** — DELETE checks ownership only, UPDATE still runs only the single-condition (boolean-only) check from the original migration. State whether this asymmetry is an accepted, reasoned decision (e.g., "deleting/correcting historical rows should not require a still-active consent flag") or a defect to register.
5. **`user_consents.consent_type`'s CHECK constraint is diffed against every place a consent-type value is asserted or required.** The DB constraint (`20260702000000_dpdp_user_consents.sql:25`) and the API's `Literal["attention_tracking", "learner_dna"]` (`apps/api/app/modules/assessment/schemas.py:191`) agree with each other — confirm this. But Epic-5's own DoD requires a `'data_processing'` consent row at signup and CLAUDE.md/epic-5 both use the name `'attention_capture'` where the DB and code actually use `'attention_tracking'`. The audit report names this mismatch explicitly as doc-vs-code drift (or a missing migration) rather than silently treating the epic doc as correct.
6. **No table is reachable by an unauthenticated (anon-key, no JWT) request** — verified against the live project, not inferred from "RLS is enabled." Report the actual anon-role query result (expect: 0 rows, every table) as evidence, not a restated assumption.
7. **Storage bucket access is audited alongside table RLS.** All 4 buckets (`source-pdfs`, `lesson-images`, `lesson-audio`, `avatar-clips`) are `public = false` (`20260710000000_storage_buckets.sql`); no migration defines an explicit `storage.objects` RLS policy for any of them (confirmed by repo-wide search — zero hits). Verify against the live project that this means anon/authenticated get zero direct access by Supabase's own RLS-enabled-by-default posture on `storage.objects`, and confirm the only real access path is signed URLs issued server-side (media router, service-role key) — cite the actual file.
8. **Privileged SQL functions are re-verified against live grants, not just migration text.** `merge_lesson_job_node_output` (`20260713020000...sql`) and `increment_learner_dna_session_count` (`20260813000001...sql`) both `REVOKE EXECUTE` from `public`/`anon`/`authenticated` and `GRANT` only to `service_role` in their migration files — confirm this is still true in the live project's `information_schema.routine_privileges` (a dashboard-side grant could silently widen this after the fact). Confirm the two `SECURITY DEFINER` trigger functions (`handle_new_auth_user`, `sync_attention_consent_on_insert`) are `RETURNS TRIGGER` and therefore cannot be invoked as direct RPCs at all — state this as a positive finding, not a gap.
9. **Audit report is committed** at `docs/security/rls-audit.md` (directory does not exist yet — confirmed via repo search) containing: the per-table matrix from AC1-3, the consent-gate findings from AC4-5, the anon-access evidence from AC6, the storage findings from AC7, the function-grant findings from AC8, and an explicit "Not Yet Applicable" section naming `lesson_access`, `stripe_events`, `profiles.is_admin` with their trigger (Story 5-3 / a future admin-panel story).
10. **Every real gap found gets a `D-nn` register entry**, not a bare note in the audit doc — per `CLAUDE.md` binding rule 5 ("a documented limitation is NOT an accepted one... every KNOWN LIMITATION must carry a `D-nn` register ID"). At minimum, the `consent_type` naming/value mismatch (AC5) and the `attention_events` DELETE/UPDATE consent-check asymmetry (AC4), if judged unintentional, are registered in `docs/DEFECT-REGISTER.md` with owner and trigger, not just described.

## Scale & Load

1. **What is ONE unit of work, and what is its range?** One unit of work is one table's full policy verification: authenticate as 3 fixed principals (owner, stranger, anon/no-JWT) against the live Supabase project and confirm SELECT/INSERT/UPDATE/DELETE behave as the policy predicate says. Range: min is `user_consents` (2 policies only — SELECT+INSERT, immutable by design), typical is a single-hop table (`users`, `lessons`, `books`, `sessions`, `learner_dna`, `onboarding_responses`, `user_notification_preferences` — 4 policies, direct `user_id = auth.uid()`), largest/most complex is `attention_events` (4 policies, 2-table join `sessions → users`, plus a second `EXISTS` against `user_consents` on INSERT only — the deepest predicate in the schema). This audit is a one-time verification pass per migration-affecting change, not a per-request runtime cost, so its own "range" is bounded by the table count (15 today, growing only when a new migration lands), not by student volume.
2. **Which budgets are FIXED while the input VARIES — and what happens past them?** The audit harness fixes exactly 3 test principals per table (owner / stranger / anon) — this is a deliberate, explicit budget: it is the minimum needed to prove both "owner sees only their own row" and "no one else sees it," and adding more strangers proves nothing additional, so 3 is not a truncation, it is the correct saturation point and should be documented as such. Separately: none of the RLS predicates themselves impose a token/character/row budget — Postgres evaluates a policy's `USING`/`WITH CHECK` boolean per row inside the planner, not as a separate materializing fetch, so there is no analogous "silent truncation" surface inside RLS the way there is in the pipeline's `_get_section_body(max_chars=6000)`. State this explicitly in the audit report rather than leaving it unstated, since the Scale Contract's Q2 concern (a fixed cap silently degrading a variable input) does not apply to RLS the way it does to LLM-context assembly — but the audit report must say so, not assume a reader infers it.
3. **What is the SCOPE of every limit — per user, per instance, or per deployment?** RLS policies are enforced inside Postgres itself, evaluated per statement — they are correct regardless of how many FastAPI/Railway replicas issue the request, so unlike D49 (`RATE_LIMIT_STORAGE_URL=memory://` multiplying per replica) or D52 (rate limiter keyed by IP, shared across users), there is no per-instance drift risk here: one Postgres database is the single source of truth for every replica. The audit itself is scoped per-deployment — there is exactly one live Supabase project today, so "verify against the live project" means one run, not N.
4. **Which reads and writes are UNBOUNDED?** Every ownership-check predicate in every policy is an `EXISTS (SELECT 1 FROM ... WHERE ...)` — bounded by definition (short-circuits on the first match, never materializes a row set). No policy in any of the 14 migrations does an unbounded `SELECT` inside its predicate. This is a distinct layer from `tests/unit/test_unbounded_queries.py`'s scope (which scans `app/modules/*/router.py` and `app/modules/*/service.py` for unbounded reads in application code) — this story does not duplicate that guard, it verifies the RLS predicate layer sitting beneath those same request paths, and the audit report should note the boundary explicitly so a future reviewer doesn't assume one guard covers both layers.
5. **Which caps were INHERITED from an earlier design, and have they been re-derived?** Two real cases found by reading the migrations, not assumed: (a) `chapters`/`chunks` RLS was correctly re-rooted from `lessons.user_id` to `books.user_id` in `20260803000000_chapters_book_scoped.sql` when the unit of ingestion changed from "one lesson" to "one book" (Story 1-9) — this re-derivation was already done and this audit's job is only to confirm no stale lesson-rooted policy was missed elsewhere. (b) `user_consents.consent_type`'s CHECK constraint was sized for exactly 2 values at Sprint 1 (Story 3-17, `20260702000000_dpdp_user_consents.sql:25`) and was **never re-derived** when Epic-5's later DoD called for a 3rd value (`'data_processing'`, written at signup) — this is an un-re-derived inherited cap and AC5/AC10 require it be named, not silently worked around by inventing a value the DB would reject with a 23514 CHECK-violation.
6. **Is every check-then-act sequence safe under CONCURRENT requests?** RLS itself has no check-then-act race: Postgres evaluates `USING`/`WITH CHECK` atomically within the same statement that reads or writes, so there is no read-then-write gap for RLS enforcement to fall into (unlike D45's `(chapter_id, tier)` idempotency pre-check, which is application-code doing a separate SELECT before an INSERT). The two SECURITY DEFINER/INVOKER RPC functions this audit reviews were themselves written specifically to close prior read-modify-write races: `merge_lesson_job_node_output` (`20260713020000...sql`) replaced a client-side read-modify-write of `lesson_jobs.node_outputs` that silently lost writes under concurrent Phase-1 dispatch; `increment_learner_dna_session_count` (`20260813000001...sql`) replaced a Python-side read-then-write of `session_count` for the identical reason. Both are now single-statement atomic `UPDATE`s. The one remaining check-then-act-shaped object is the `sync_attention_consent_on_insert` AFTER INSERT trigger, which does a separate `UPDATE public.users SET attention_consent = true` inside the trigger body — verify explicitly (not assume) that two concurrent consent-insert calls for the same user cannot leave `attention_consent` inconsistent: since every write sets the same literal `true`, this is idempotent by construction and cannot race to a wrong value, but the audit report must state this reasoning rather than leave the reader to assume it.

## Dev Notes

- **Relevant architecture patterns and constraints.** RLS is the sole DB-level access control layer (CLAUDE.md §18: "RLS on ALL Supabase tables — users read only their own data"). The app itself uses the `service_role` key server-side (bypasses RLS entirely by design — `apps/api/app/core/db.py`), so RLS is what protects direct PostgREST/Supabase-client access from a browser using the `anon`/`authenticated` key, not what protects the FastAPI backend from itself. The dev1-tracker's existing claim ("RLS enabled on all Supabase tables ✅ ... attention_events RLS gates on attention_consent = true ✅") is exactly the kind of unverified assertion CLAUDE.md's Defect Register section warns about ("9 of 11 pre-existing defects never worked for one minute") — this story exists to turn that checkmark into evidence.
- **Source tree components to touch.** New file only: `docs/security/rls-audit.md`. No application code changes are in scope for this story — any real defect found (e.g., the `consent_type` mismatch) is registered in `docs/DEFECT-REGISTER.md` and left for a separate fix story, per the Story-First Gate's separation of story-writing from implementation. Test harness code (if written as a reusable script rather than a manual run) would live under `apps/api/tests/integration/` alongside the existing `supabase_shim.sql`.
- **Testing standards summary.** Per binding rule 4 ("any code naming a DB table/column must be validated against `supabase/migrations/`") every table/column claim in the audit report must cite the exact migration file and line. Per binding rule 3, no verdict in the audit report should rest solely on the Postgres shim — D38's own text is explicit that the shim's fidelity to Supabase's real `auth.uid()`/role behavior is unproven by any test that could disconfirm it, so this story's verification step must run against the real live project (a shim-only pass would just reproduce D38's original gap for the other 13 tables).
