## Scale & Load

1. **What is ONE unit of work, and what is its range?** One unit of work is one table's full policy verification: authenticate as 3 fixed principals (owner, stranger, anon/no-JWT) against the live Supabase project and confirm SELECT/INSERT/UPDATE/DELETE behave as the policy predicate says. Range: min is `user_consents` (2 policies only â€” SELECT+INSERT, immutable by design), typical is a single-hop table (`users`, `lessons`, `books`, `sessions`, `learner_dna`, `onboarding_responses`, `user_notification_preferences` â€” 4 policies, direct `user_id = auth.uid()`), largest/most complex is `attention_events` (4 policies, 2-table join `sessions â†’ users`, plus a second `EXISTS` against `user_consents` on INSERT only â€” the deepest predicate in the schema). This audit is a one-time verification pass per migration-affecting change, not a per-request runtime cost, so its own "range" is bounded by the table count (15 today, growing only when a new migration lands), not by student volume.
2. **Which budgets are FIXED while the input VARIES â€” and what happens past them?** The audit harness fixes exactly 3 test principals per table (owner / stranger / anon) â€” this is a deliberate, explicit budget: it is the minimum needed to prove both "owner sees only their own row" and "no one else sees it," and adding more strangers proves nothing additional, so 3 is not a truncation, it is the correct saturation point and should be documented as such. Separately: none of the RLS predicates themselves impose a token/character/row budget â€” Postgres evaluates a policy's `USING`/`WITH CHECK` boolean per row inside the planner, not as a separate materializing fetch, so there is no analogous "silent truncation" surface inside RLS the way there is in the pipeline's `_get_section_body(max_chars=6000)`. State this explicitly in the audit report rather than leaving it unstated, since the Scale Contract's Q2 concern (a fixed cap silently degrading a variable input) does not apply to RLS the way it does to LLM-context assembly â€” but the audit report must say so, not assume a reader infers it.
3. **What is the SCOPE of every limit â€” per user, per instance, or per deployment?** RLS policies are enforced inside Postgres itself, evaluated per statement â€” they are correct regardless of how many FastAPI/Railway replicas issue the request, so unlike D49 (`RATE_LIMIT_STORAGE_URL=memory://` multiplying per replica) or D52 (rate limiter keyed by IP, shared across users), there is no per-instance drift risk here: one Postgres database is the single source of truth for every replica. The audit itself is scoped per-deployment â€” there is exactly one live Supabase project today, so "verify against the live project" means one run, not N.
4. **Which reads and writes are UNBOUNDED?** Every ownership-check predicate in every policy is an `EXISTS (SELECT 1 FROM ... WHERE ...)` â€” bounded by definition (short-circuits on the first match, never materializes a row set). No policy in any of the 14 migrations does an unbounded `SELECT` inside its predicate. This is a distinct layer from `tests/unit/test_unbounded_queries.py`'s scope (which scans `app/modules/*/router.py` and `app/modules/*/service.py` for unbounded reads in application code) â€” this story does not duplicate that guard, it verifies the RLS predicate layer sitting beneath those same request paths, and the audit report should note the boundary explicitly so a future reviewer doesn't assume one guard covers both layers.
5. **Which caps were INHERITED from an earlier design, and have they been re-derived?** Two real cases found by reading the migrations, not assumed: (a) `chapters`/`chunks` RLS was correctly re-rooted from `lessons.user_id` to `books.user_id` in `20260803000000_chapters_book_scoped.sql` when the unit of ingestion changed from "one lesson" to "one book" (Story 1-9) â€” this re-derivation was already done and this audit's job is only to confirm no stale lesson-rooted policy was missed elsewhere. (b) `user_consents.consent_type`'s CHECK constraint was sized for exactly 2 values at Sprint 1 (Story 3-17, `20260702000000_dpdp_user_consents.sql:25`) and was **never re-derived** when Epic-5's later DoD called for a 3rd value (`'data_processing'`, written at signup) â€” this is an un-re-derived inherited cap and AC5/AC10 require it be named, not silently worked around by inventing a value the DB would reject with a 23514 CHECK-violation.
6. **Is every check-then-act sequence safe under CONCURRENT requests?** RLS itself has no check-then-act race: Postgres evaluates `USING`/`WITH CHECK` atomically within the same statement that reads or writes, so there is no read-then-write gap for RLS enforcement to fall into (unlike D45's `(chapter_id, tier)` idempotency pre-check, which is application-code doing a separate SELECT before an INSERT). The two SECURITY DEFINER/INVOKER RPC functions this audit reviews were themselves written specifically to close prior read-modify-write races: `merge_lesson_job_node_output` (`20260713020000...sql`) replaced a client-side read-modify-write of `lesson_jobs.node_outputs` that silently lost writes under concurrent Phase-1 dispatch; `increment_learner_dna_session_count` (`20260813000001...sql`) replaced a Python-side read-then-write of `session_count` for the identical reason. Both are now single-statement atomic `UPDATE`s. The one remaining check-then-act-shaped object is the `sync_attention_consent_on_insert` AFTER INSERT trigger, which does a separate `UPDATE public.users SET attention_consent = true` inside the trigger body â€” verify explicitly (not assume) that two concurrent consent-insert calls for the same user cannot leave `attention_consent` inconsistent: since every write sets the same literal `true`, this is idempotent by construction and cannot race to a wrong value, but the audit report must state this reasoning rather than leave the reader to assume it.
